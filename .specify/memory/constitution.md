# qurioth-toybox 開発原則 (Constitution)

このドキュメントは `qurioth-toybox` における Spec-Driven Development の judged 基準となる原則を
定義する。`/specify` `/plan` `/tasks` の各フェーズ、および実装レビューはこの原則に照らして行う。

## このプロジェクトの性質

- 一人のオーナーが自分のペースで育てる個人開発の「おもちゃ箱」サイト。TRPG(テーブルトークRPG)の
  セッション準備・記録ツールと、写真等の個人コンテンツ置き場を兼ねる。
- 利用者はほぼ自分自身、または同じTRPGコミュニティの知人。エンタープライズ的な堅牢性より、
  すぐ動く・楽しく作れることを優先してよい。

## 原則

### 1. 過剰実装をしない (YAGNI)

依頼された機能に対して必要十分な実装を行う。将来の拡張を見越した抽象化・設定項目・汎用化は、
明確に要求されない限り作らない。個人開発の速度を落とす複雑さは負債になる。

### 2. 既存の慣習に合わせる

新規ページは `src/app/<domain>/page.tsx` の Next.js App Router 規約に従い、`trpg/page.tsx` の
`toolCards` / `libraryCards` のようなカード一覧から辿れるようにする。コンポーネントは
`src/components/` 配下に用途別(forms/, recharts/ 等)またはトップレベルに配置する。UI文言は
日本語を基本とする。詳細は [CLAUDE.md](../../CLAUDE.md) を参照。

### 3. 仕様は「なぜ」を残す

`spec.md` には要件と背景(なぜ必要か)を書き、実装方法(どう作るか)は `plan.md` に分離する。
実装の途中で仕様と食い違いが生じたら、コードではなく仕様を先に見直す。

### 4. 大きな判断は ADR に

依存ライブラリの入れ替え、データ構造の破壊的変更、認証や外部サービス連携の追加など、後戻りに
コストがかかる判断をしたときは [docs/adr/](../../docs/adr/) に ADR を追加する。

### 5. 小さな変更にはこのフローを課さない

typo修正、依存パッケージ更新、スタイル微調整などは `/specify` からのフローを経由せず直接
実装してよい。SDDは「ある程度まとまった機能追加・変更」に適用する。

### 6. テスト・CI は無理に完備を目指さない

現状 CI は Renovate のみで lint/build/test は手動実行が前提([CLAUDE.md](../../CLAUDE.md) 参照)。
テストを書くこと自体を否定はしないが、個人開発のスコープに見合わない重厚なテスト基盤を目的化
しない。

## ガバナンス

この Constitution は本プロジェクトのオーナー(開発者本人)がいつでも改訂できる。改訂した場合は
このファイルを直接更新し、大きな方針転換であれば ADR にも理由を残す。
