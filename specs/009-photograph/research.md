# Research: 写真一覧(アルバム単位)

**Feature**: [spec.md](spec.md) | **Plan**: [plan.md](plan.md) | **Date**: 2026-11-08

保管先と取り込み手順の大枠は [ADR-0017](../../docs/adr/0017-store-photos-in-r2.md) で決めた。
ここでは、それを実装に落とすときの判断を記録する。

## R1. 縦横混在の並べ方(FR-005 / FR-006 / FR-007 / FR-009)

- **Decision**: 行の高さを揃えて並べる(Google フォトや Flickr の形)。写真を登録順に左から並べ、
  目安の高さで並べた幅(写真の幅の合計 + 隙間)が表示幅に達したところで行を区切る。その行の写真が
  ちょうど表示幅に収まるよう、行の高さを「(表示幅 − 隙間の合計)÷ 縦横比(幅 ÷ 高さ)の合計」に
  揃える。最後の行は目安の高さのまま左に寄せる。目安の高さは 420px で、表示幅の半分を超えないよう
  にする。行の組み方は純粋関数(`justifyRows`)にする。写真は切り取らない。
- **Rationale**:
  - 実装の途中(2026-11-08)で、オーナーから「横長の写真が小さく感じる」と要望があった。列の幅を
    揃える並べ方では、横長(3:2)の面積は縦長(2:3)の約 0.44 倍にしかならない。Dropbox に載せていた
    72枚のうち52枚が横長で、大半の写真が小さく表示されていた。
  - 比較用の一時ページで、本物の写真(ペンギン水族館の13枚)を使って3案を見比べ、オーナーがこの案と
    行の高さ 420px を選んだ。表示幅 945px では、横長だけの行の1枚が約 465×261px(高さ 280px 時)に
    なり、4列表示(約 225×150px)の約3.6倍の面積になった。
  - 行の右端が揃うので、「列の下端がずれる」問題も起きない。並び順も左上から右へ素直に読める。
  - 「表示幅の半分を超えない」制限で、幅375pxの端末でも1行に2枚前後が並ぶ(目安 420px のままだと、
    横長1枚で表示幅を超えて1行1枚になる)。
- **Alternatives considered**:
  - 写真を最も短い列へ入れて、列の幅を揃える(最初の実装)。列の下端のずれは直ったが、上のとおり
    横長が小さく見えた。
  - 列の幅を揃えたまま3列に減らす。全体は大きくなるが、縦長も同じ割合で大きくなり、縦長と横長の
    差は変わらない。
  - 横長だけ2列分の幅にする。マス目に収めようとすると、穴が空いたり順番が入れ替わったりしやすい。
  - CSS の `columns`。上から下へ流し込むため、写真を足すたびに全体の列が組み変わる(FR-009 違反)。
  - 正方形に切り抜く。拡大表示がないので写真の一部が見えなくなる(FR-006 違反)。
- **続きの読み込みとの関係**: 行の組み方は先頭から順に決まるので、続きを足しても、それまでの最後の行
  より前の行は変わらない。最後の行は、続きの写真と合わせて組み直される(spec FR-009)。

## R2. 表示幅の測り方と、開いた直後の組み直し(FR-005 / Edge Cases)

- **Decision**: 写真を並べる領域の幅を、ブラウザで測ってから行を組む。領域の要素は常に描き、
  `useLayoutEffect` で最初の幅(`clientWidth`)を読み、以後は `ResizeObserver` で幅の変化を追う。
  幅が分かるまで(サーバーでの描画とハイドレーション中)は写真を並べず、場所だけ確保した枠を出す。
- **Rationale**:
  - 行の高さは表示幅から決まるので、幅が分からないと組めない。CSS だけでは R1 の組み方を表せない。
  - `useLayoutEffect` は描画の前に走るので、ハイドレーションの直後に幅を読んで並べても、空の枠が
    一瞬見えるだけで、写真が並んでから組み直されることはない。
  - 端末の回転やウィンドウの大きさの変更には `ResizeObserver` で追従する(Edge Cases)。
- **Alternatives considered**:
  - 画面幅から決めた固定の幅で組む。サイトの余白やスクロールバーの有無で実際の幅とずれ、行の右端が
    揃わなくなる。
  - 最初の実装で使った、列数(2 / 4)を `matchMedia` から求めるフック(`use-column-count.ts`)。
    列で並べなくなったので不要になり、削除した。

## R3. 画像の大きさと読み込ませ方(FR-013 / SC-006)

- **Decision**: 写真1枚につき、幅 640px と幅 1280px の2つの WebP を作る(元が小さければ拡大しない)。
  一覧では `<img srcset sizes>` を使い、表示幅と画面の解像度に合わせてブラウザに選ばせる。
  `loading="lazy"` と `decoding="async"` を付ける。
- **Rationale**:
  - 拡大表示がない(spec の前提)ので、要るのは一覧の1枠に足りる大きさだけ。行の高さ 420px のとき、
    横長1枚の幅は最大で約 630px、縦長は約 280px。幅 640px なら解像度1倍の画面には足り、解像度2倍の
    画面の横長には 1280px を出す。`sizes` には写真ごとの表示幅をそのまま書く。
  - ADR-0017 の「長辺1600px と 600px」は試す前の目安だった。拡大表示がない以上、1600px は使い道がない。
    幅で揃えると `srcset` の `w` 指定とそのまま対応する。ADR-0017 の記述もこれに合わせて直す。
  - `next/image` は使わない。既存どおり `unoptimized` で使うなら利点は場所の確保だけで、`<img>` の
    `width` / `height` で足りる。`srcset` を2つの幅に絞るには独自の loader と幅の設定が要り、過剰。
    Biome の `noImgElement` は、既存のコードと同じく理由を書いて抑止する。
- **Alternatives considered**:
  - 1枚だけ(幅 1280px)作る。スマホでは必要の4倍の画素を読むことになり、SC-006 を満たしにくい。
  - `<picture>` で AVIF と WebP を出し分ける。生成とアップロードが倍になる。WebP で十分小さい。

## R4. 画像を作る道具(撮影情報の削除・向き・色)

- **Decision**: `sharp` で作る。`rotate()`(引数なし)で撮影時の向き情報に合わせて回転し、
  `resize({ width, withoutEnlargement: true })`、`webp({ quality: 80 })` で書き出す。
  `withMetadata` / `keepMetadata` は呼ばない。`sharp` は devDependencies に明示して入れる。
- **Rationale**:
  - `sharp` は、明示的に残さない限り撮影情報を書き出さない(FR-014 / SC-007)。出力は sRGB になる。
  - `next` が任意の依存として既に `sharp` を入れており、`pnpm-workspace.yaml` でビルドも許可済み。
    ただしスクリプトから直接使う以上、`package.json` に明示する。
  - 画質80と2つの幅は目安。実際の写真(ネモフィラなど)で `--dry-run` の合計サイズと見た目を確かめて
    決める。
- **リスク**: 一眼の JPEG が Adobe RGB で、色の情報をファイルに埋め込んでいない場合、sRGB への変換で
  色がくすむことがある。最初のアルバムで元の写真と見比べる。
- **Alternatives considered**: ImageMagick などの外部コマンドを呼ぶ。PC ごとに導入が要り、
  Windows でのパスの扱いも面倒になる。

## R5. 画像のキーと R2 上の置き方

- **Decision**: 元の写真ファイルの中身の SHA-256 の先頭16文字(16進数)をキーにする。R2 には
  `<キー>-640.webp` と `<キー>-1280.webp` を置く。アルバムの区切りはキーに含めない。
- **Rationale**:
  - 元の写真のフォルダ名を変えても、キーは変わらない(ADR-0017)。
  - 同じ写真を2つのアルバムに入れても、R2 には1組だけ置く。
  - 中身が変われば(現像し直したら)別のキーになり、ブラウザのキャッシュ(1年・immutable)と
    食い違わない。
  - 64ビット分あれば、数千枚の規模で衝突は事実上起きない。
- **Alternatives considered**: 圧縮後の WebP の中身でキーを作る。`sharp` の版や画質の設定が変わると
  同じ写真でもキーが変わり、全写真が上げ直しになる。

## R6. R2 へのアップロード

- **Decision**: R2 の S3 互換 API を、`aws4fetch`(リクエストに署名するだけの小さなライブラリ)で
  呼ぶ。使うのは PUT(アップロード)と DELETE(`--prune`)だけ。接続先は
  `https://<アカウントID>.r2.cloudflarestorage.com/<バケット>/<キー>`、リージョンは `auto`。
  アップロード済みかどうかは、コミット済みのアルバムデータにキーがあるかで判断し、R2 に問い合わせない。
- **Rationale**:
  - Cloudflare の R2 の資料に、JavaScript から使える手段として載っている。依存が小さい。
  - `wrangler r2 object put` は1回に1ファイルで、100枚(200ファイル)だとコマンドの起動だけで数分かかる。
  - アルバムデータが「何を上げたか」の記録を兼ねるので、R2 の一覧を取る操作は要らない。
- **リスク**: Cloudflare の資料で確認できた `aws4fetch` の例は、署名付き URL を作るものだけだった。
  最初の1枚で、直接の PUT が通ることを確かめる。通らなければ `@aws-sdk/client-s3`(R2 の資料に
  PUT の例がある)に替える。
- **Alternatives considered**: `@aws-sdk/client-s3`。資料は手厚いが、依存がずっと大きい。

## R7. 配信する Worker

- **Decision**: `workers/photo/` に Worker を置く。GET と HEAD だけを受け付け、パスが
  `<16文字の16進数>-(640|1280).webp` の形のときだけ R2 から返す。それ以外は 404 を返す。
  レスポンスには `Content-Type: image/webp`、`Cache-Control: public, max-age=31536000, immutable`、
  `ETag` を付ける。型は Worker が使う部分だけをファイル内に書き、`@cloudflare/workers-types` は
  入れない。デプロイは `pnpm dlx wrangler deploy` で行い、`wrangler` は依存に入れない。
- **Rationale**:
  - パスの形を絞ると、R2 にある他のものを読まれる心配がない。一覧の取得や書き込みの手段も持たない
    (ADR-0017)。
  - 20行ほどの Worker のために大きな型定義パッケージを入れると、リポジトリの型チェック
    (`tsc --noEmit` は `**/*.ts` を対象にする)と食い違う。必要な型だけ書けば、今の `tsconfig.json`
    のまま通る。
  - デプロイはたまにしか行わないので、`dlx` で十分。
- **リスク**: `*.workers.dev` の Worker から R2 を読めることは、公式資料で直接は確認できていない
  (ADR-0017)。最初に1枚で確かめる。

## R8. リスト(txt)の書式と読み方

- **Decision**: 1行に1枚。先頭の `# title:` / `# date:` をアルバムの情報として読み、それ以外の `#` で
  始まる行と空行は無視する。行の前後の空白と、前後を囲む `"` は取り除く。区切りは `\` と `/` の
  どちらも受け付ける。`PHOTO_SOURCE_ROOT` の下を指す絶対パスは相対パスに直し、リストを書き換えて
  その旨を表示する。`PHOTO_SOURCE_ROOT` の外を指す絶対パスはエラーにする。同じ写真が2回書かれて
  いたら、2回目を無視して知らせる。読み方は純粋関数(`parsePhotoList`)にしてユニットテストを書く。
- **Rationale**:
  - エクスプローラーの「パスとしてコピー」をそのまま貼れることが、オーナーの手間を減らす要。
  - リストを相対パスに直しておけば、PC やドライブが変わっても `.env.local` の1行で済む。
  - 書き間違いは `--dry-run` で全部まとめて出し、1件でもあれば本番の実行をしない。
- **Alternatives considered**: CSV にする。キャプションを持たない(spec の前提)ので列が要らない。

## R9. 似ている写真の見分け方

- **Decision**: 「撮影時刻が30秒以内」かつ「8×8 の白黒の明るさの並びの相関(平均を引いて長さ 1 に
  揃えた値の内積)が 0.6 以上」の組を連写とみなし、つながった写真を1グループにまとめる。撮影時刻は
  元の写真の Exif の日時のうち最も早いもの(撮影時刻は現像の書き出し時刻より早い)。撮影時刻の
  分からない写真は比べない。比べるのはそのリストの中だけ。比較とグループ分けは純粋関数にして
  ユニットテストを書く。
- **Rationale**:
  - 実装時(2026-11-08)に実際の写真37枚(現像済みのネモフィラ12枚、子々川の連続した12枚、
    ペンギン水族館13枚)で確かめた。
  - ほぼ同じ連写の2枚(人物が少し動いただけ)は、撮影時刻が3秒差で、相関は 0.84。
  - 画像だけで比べると、別の被写体でも明るさの配置や色が近いと連写と区別できなかった。白黒の相関では
    チンアナゴとペンギン(撮影時刻は30分差)が 0.84 で、連写の組と同じだった。色も含めると、
    「どれも青い水中」のウミガメ・ペンギン・クラゲ(数分〜45分差)が 0.8 前後になった。
    連写は数秒以内に撮るので、撮影時刻で候補を絞ると、こうした誤検出がすべて消えた。
  - 計算が軽く、数百枚の総当たりでも一瞬で終わる。追加の依存が要らない(`sharp` と、ファイルの先頭の
    文字列から日時を拾うだけ)。
  - 知らせるだけで削除はしない(ADR-0017)ので、多少の見逃しや拾いすぎは許容できる。時刻を空けて
    撮り直した似た写真は拾えないが、オーナーが選ぶ段階で気づける。
- **Alternatives considered**:
  - 差分ハッシュ(dHash)。計画の段階ではこれを選んだが、ほぼ同じ連写の2枚の距離(64ビット中18、
    割合 0.28)と、まったく別の写真の組の距離(最小 22、割合 0.31)がほとんど変わらず、閾値で
    分けられなかった。16×16(256ビット)にすると、さらに差が縮んだ。
  - 画像の相関だけで比べる(実装の途中で一度採用した)。上のとおり、別の被写体を拾った。
  - 機械学習の特徴量で比べる。精度は高いが、モデルと依存が大きく、この用途には過剰(原則1)。

## R10. アルバムデータの形と、画面からの読み方

- **Decision**: アルバムごとに `src/data/photograph/albums/<slug>.json` を生成する。加えて、全アルバムを
  import して並べる `src/data/photograph/albums/index.ts` もスクリプトが生成する。どちらも書き出した
  あとに Biome で整形する。
- **Rationale**:
  - 画面は `index.ts` を import するだけで、型の付いたデータを得られる。実行時にファイルを読まない。
  - アルバムを足すたびに手で登録する手間がない(シナリオの `scenario-list.ts` のような登録漏れが
    起きない)。
  - 生成したファイルを整形しないと、CI の `pnpm format:check` が落ちる。
- **Alternatives considered**:
  - ページで `fs` を使ってフォルダを読む。ビルド時には動くが、テストや型の扱いが面倒になる。
  - 全アルバムを1つの json にまとめる。差分が読みにくくなり、同時に2つのアルバムを触ったときに
    衝突しやすい。

## R11. アルバムの画面のルーティング(FR-015)

- **Decision**: `src/app/other/photograph/[album]/page.tsx` を作る。`generateStaticParams` で全アルバムの
  ページをビルド時に作り、`dynamicParams = false` で、それ以外の URL を 404 にする。ページは
  サーバーコンポーネントにし、表示件数と列数を扱う部分だけをクライアントコンポーネントに分ける。
- **Rationale**: アルバムはビルド時に決まっていて、実行時に増えない。存在しない URL を Next.js の
  既定の 404(サイト共通の表示)に任せられる。
- **Alternatives considered**: ページ内で見つからないときに `notFound()` を呼ぶ。`dynamicParams = false`
  なら呼ぶ必要がない。

## R12. 続きの読み込み

- **Decision**: スクロール量を `scroll` イベントで見る今の方式をやめ、リプレイ一覧
  (`src/app/trpg/replay/page.tsx`)と同じく、一覧の下に置いた目印を `IntersectionObserver` で
  見張る。件数は20件のまま。
- **Rationale**:
  - 今の方式は、読み込み中の印を500ms後に戻すタイマーに頼っていて、間隔の決め方に根拠がない。
  - リプレイ一覧と同じ書き方に揃う(原則2)。`vitest.setup.ts` にスタブもある。
- **Alternatives considered**: 今の方式を残す。動いてはいるが、改修のついでに直すほうが安い。
