# Spec: テスト基盤の導入(テスティングトロフィー戦略)

## ステータス

Draft

## 背景・目的

`qurioth-toybox` はこれまで実装方針を明文化せず、思いついたまま機能を継ぎ足してきた
(CLAUDE.md記載の通り)。今後リファクタリングを行いたいが、テストが一切無い状態では、
変更のたびに全ページを手動でブラウザ確認するしかなく、見落としによる回帰のリスクが高い。

リファクタリングを安全に行うための回帰検知の仕組みとして、テスト基盤を導入する。戦略には
「テスティングトロフィー」(静的解析を土台に、結合テストを主軸とし、ユニットテストとE2Eは
必要な分だけ)を採用する。このプロジェクトは既にTypeScript strict + Biome lintを持っており、
トロフィーの土台部分は揃っている。次のレイヤーとして、既存のロジック(ユーティリティ関数・
状態を持つコンポーネント)を対象にした結合テスト・ユニットテストを追加する。

## スコープ

### やること

- テストランナー(Vitest を想定)と、コンポーネントの結合テストに必要なライブラリを導入する。
- 既存の複雑なロジックを持つユーティリティ関数(例: `src/utils/grep-utils.ts`、
  `src/utils/convert-utils.ts` など、CCFOLIAログ解析やダイスログ変換のような純粋関数)に
  ユニットテストを追加する。
- 状態やロジックを持つコンポーネント(例: `CharacterCard`のフリップ・スキル集計処理、
  `ccfolia-grep`ページの集計ロジックなど)に、実際の入力に近いデータを使った結合テストを
  追加する。
- CI(`.github/workflows/ci.yml`)にtest実行ステップを追加し、失敗時にワークフローが
  失敗するようにする。
- テスト戦略(テスティングトロフィー採用)とテストランナー(Vitest採用)の技術判断を
  ADRに記録する(constitution.md 原則4: 後戻りにコストがかかる技術判断はADR化する)。
- 「何をテストし、何をテストしないか」の判断基準(テスティングトロフィーの考え方)を
  ドキュメント(CLAUDE.mdまたはADR)に残す。

### やらないこと

- E2Eテスト(Playwright等)の導入。テスティングトロフィーの最上層にあたるが、今回は
  スコープ外とし、必要になった時点で別途検討する。
- 全関数・全コンポーネントの網羅的なテスト(カバレッジ100%等の数値目標)。個人開発の
  スコープに見合わない重厚化はしない(constitution.md 原則6)。
- 既存コードの実装そのものをリファクタリングすること。今回はテスト基盤とテストの追加のみで、
  リファクタリング本体は別スペックで行う。
- スナップショットテストを主軸にすること。DOM構造の些細な変更で壊れやすく、
  テスティングトロフィーが重視する「意味のある回帰検知」との相性が悪いため避ける。

## ユーザーストーリー / シナリオ

- サイトオーナーとして、既存のユーティリティ関数と状態を持つコンポーネントにテストの
  安全網が欲しい。そうすればリファクタリングのたびに全ページを手動確認しなくても、
  壊れていないと確信を持てるから。
- サイトオーナーとして、テストがCIで自動実行されてほしい。そうすればレビュー前に
  回帰に気づけるから。

## 受け入れ条件

- [ ] `pnpm test` でテストランナーが実行できる。
- [ ] `grep-utils.ts`、`convert-utils.ts` など既存の複雑なロジックを持つ関数に対する
      ユニットテストが存在し、パスする。
- [ ] 状態やロジックを持つコンポーネント(`CharacterCard`等)に対する結合テストが
      最低1つ存在し、パスする。
- [ ] CI(`ci.yml`)で `pnpm test` が実行され、テスト失敗時にワークフローが失敗する。
- [ ] テスト方針(テスティングトロフィーの考え方、何をテストする/しないかの判断基準)が
      ドキュメントに記録されている。
- [ ] テスト戦略・テストランナーの選定理由がADRとして `docs/adr/` に記録されている。

## 制約・前提

- 個人開発のスコープに見合わない重厚なテスト基盤を目的化しない(constitution.md 原則6)。
- 過剰実装をしない、既存の慣習に合わせる(パッケージマネージャはpnpm、lintはBiome、
  Next.js App Router)。
- 既存のCI(`.github/workflows/ci.yml`)にtestステップを統合する。新規ワークフローは
  作らない。

## オープンな疑問

- 最初のテスト対象とする関数・コンポーネントの優先順位(どこから着手するか)は `/plan` or
  `/tasks` で具体化する。
- constitution.md 原則6「現状 CI は Renovate のみで lint/build/test は手動実行が前提」は
  ADR-0004/0005/0007でのCI導入により実態と合わなくなっている。今回の作業と合わせて
  constitution.md を更新するか、別途確認したい。
