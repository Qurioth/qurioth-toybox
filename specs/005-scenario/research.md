# Research: シナリオ詳細画面の構造化表示

**Spec**: [spec.md](spec.md) | **Plan**: [plan.md](plan.md) | **Date**: 2026-10-02

spec が plan に委ねた判断(本文の持ち方など)と、設計時に出た未確定事項を解消する。

---

## R1. 本文の持ち方

**Decision**: 本文は今までどおり `src/data/scenario/markdown/<slug>.md` の Markdown を正とする。
詳細画面は表示時に Markdown を規約([README.md](../../src/data/scenario/README.md))に沿って
解釈し、構造(章・場面・NPC・エンディングなど)を組み立てて表示する。「移行」とは、
Markdown を構造化表示の前提(後述の [contracts/structured-markdown.md](contracts/structured-markdown.md))
に合わせて整え、`scenario-list.ts` のエントリに移行済みの印を付けることを指す。

**Rationale**:

- 既存の 12 本は規約への準拠度が高い。判定表記 `**〈技能〉**` が 239 箇所、正気度喪失
  `**正気度喪失：…**` が 125 箇所、能力値は全 NPC で `STR: 55 CON: 75 …` 形式になっており、
  規約がすでに事実上の構造データになっている。
- 本文を別形式へ書き換えないので、FR-028 / SC-008(情報の欠落 0 件)を満たしやすい。
  変換作業で文言を落とす余地自体が小さい。
- 執筆体験が変わらない。新規シナリオも [template.md](../../src/data/scenario/template.md) から
  書き始められ、ADR-0014 の規約がそのまま執筆ガイドとして生きる。
- 未移行シナリオと移行済みシナリオが同じデータ形式なので、段階移行(FR-027)は印の有無だけで
  切り替えられる。

**Alternatives considered**:

| 案 | 却下理由 |
| -- | -- |
| TypeScript のオブジェクトとして本文を構造化データで持つ | 約 8,400 行を手で変換する必要があり、欠落・改変のリスクが最も高い。地の文を TS の文字列として書くのは執筆体験が悪く、規約(ADR-0014)が死文化する |
| MDX にして NPC カードなどをコンポーネントとして本文に埋め込む | 依存(MDX ローダー)が増え、本文に JSX が混ざる。見た目は全シナリオ共通(FR-015)なので、シナリオごとに部品を置き分ける表現力は不要(原則1) |
| NPC・ステータスだけ YAML / front matter に切り出し、地の文は Markdown に残す | 1 本のシナリオが 2 つの形式に分かれ、NPC の記述位置(クライマックス中の神話生物など)が本文から離れる。移行時の書き換え量も増える |

## R2. Markdown の解釈方法

**Decision**: 新しい依存は入れない。見出し(ATX 形式の `#`〜`#####`)で本文を区切る行単位の
分割関数を `src/utils/scenario-structure-utils.ts` に実装する。フェンス付きコードブロック
(作中テキスト)の中の行は見出しとして扱わない。各区画の本文は Markdown 文字列のまま保持し、
表示時に既存の `react-markdown` + `remark-gfm` で描画する。

**Rationale**:

- 構造を決めるのは見出しだけで足りる。規約で `##` = 章、`###` = NPC・調査対象・ED、
  `####` = ステータス・技能・セリフ例、と見出しレベルに意味が割り当て済み。
- 見出しは全シナリオで ATX 形式のみ(Setext 形式なし)。コードブロック内の `#` 行だけ
  注意すればよく、行単位の分割で十分に正確。
- `remark-parse` / `unified` を直接使う案は、pnpm の厳格な依存解決のために直接依存として追加が
  必要になる。mdast の位置情報から部分文字列を切り出す手間も増える。ADR-0012 で依存を整理した
  方針とも合わない。
- 区画の本文を Markdown 文字列のまま持つので、規約外の自由記述や `#####` の細分も、そのまま
  描画すれば欠落しない(FR-026)。

**Alternatives considered**:

- `remark-parse` で mdast を得て木を組み替える: 前述のとおり依存追加と実装量に見合わない。
- `rehype-slug` / `rehype-autolink-headings` で目次用の id を振る: 目次の項目は解釈結果から
  作るので、id も同じ場所で振ればよく、プラグインは不要。

## R3. 判定・正気度喪失・呪文などの強調(FR-021)

**Decision**: `react-markdown` の `components` で `strong` を差し替え、太字の中身を規約の
書式に照らして分類する。判定(`〈…〉` で始まる)、正気度喪失(`正気度喪失：` で始まる)、
出典(`_…_` を含む)のそれぞれに専用の見た目を付ける。太字の外に書かれる正気度回復
(`正気度回復: 1D6`)と、呪文 `《…》`・魔導書/アーティファクト `『…』` は、段落・リスト項目・
表のセルに含まれる文字列を走査して該当箇所を `<span>` で包む。

**Rationale**:

- 規約 4 章は「太字は GM がその場で処理すべきものの合図」と定めており、太字の中身の書式も
  決まっている。分類は文字列の前方一致で済む。
- remark プラグインで mdast を書き換える案は `@types/mdast` などの型依存が必要になる。
  React の子要素の文字列を走査する方が依存なしで書ける。
- 判定の難易度(「のハード」「のイクストリーム」)は、太字の直後の地の文に置かれる
  (`**〈STR〉** のハード`)。段落の子要素を走査する際に、判定の太字の直後の文字列が
  ` のハード` / ` のイクストリーム` で始まっていれば、その部分も判定と同じ強調で包む。
  こうして技能名と難易度をひとまとまりで示す(US5 受け入れ条件 1)。難易度の付かない判定は
  レギュラーとして扱い、難易度の表示を足さない(本文にない文言を足さないため)。

**Alternatives considered**:

- 本文を事前に独自記法(`::check[目星]{level=hard}` など)へ書き換える: 本文の書き換えが
  必要になり、R1 の利点(書き換え量最小)を失う。

## R4. 区画の種別判定

**Decision**: 見出しの文字列と位置から種別を決める。

- `##` の見出し名が規約の固定セクション名(`GM 向け情報`、`特殊 HO`、`推奨技能`、`主な NPC`、
  `シナリオの導入`、`クライマックス`、`シナリオ終了`)と一致すればその章、それ以外は場面とする。
- `###` は次の順に判定する。
  1. `主な NPC` 直下、または `#### ステータス` / `#### 技能` / `#### セリフ例` を子に持つ → 人物
     (NPC・神話生物)
  2. `ED<番号>` で始まる → エンディング
  3. `その他報酬` で始まる → その他報酬
  4. `『…』` で囲まれている → 魔導書・アーティファクト
  5. それ以外 → 調査対象(汎用)

詳細は [data-model.md](data-model.md) と [contracts/structured-markdown.md](contracts/structured-markdown.md)。

**Rationale**: NPC と神話生物は見せ方を同じにする(FR-019)ので区別しない。登場する章によらず、
ステータス類を子に持つかどうかで人物と判定すれば、クライマックス中の神話生物も同じカードに
なる(US4 受け入れ条件 3)。

**規約からのずれへの対応**: 既存本文には `## シナリオ終了報酬`(parasite)のような揺れがある。
解釈側で別名を受け付けるのではなく、移行作業で規約の名前に直す(spec Assumptions)。解釈側の
分岐を増やさずに済む。

## R5. 移行済みの印と表示の切り替え(FR-010 / FR-027 / FR-029)

**Decision**: `scenario-list.ts` の `Scenario` 型に任意プロパティ `structured?: true` を追加する。
詳細画面は `structured` が真なら構造化表示、そうでなければ従来の整形表示を出す。queen-of-the-sea
(ビギニングアイドル)には付けない。

**Rationale**: 印をデータの横に置けば、移行の単位(1 本)と切り替えの単位が一致する。
移行完了(クトゥルフ神話TRPG 7版の 11 本すべてに印が付いた状態)は、`scenario-list.ts` を
見れば判断できる。

**Alternatives considered**: 移行済み ID の一覧を別ファイルに持つ → データの所在が 2 箇所に
分かれるだけで利点がない。

## R6. 目次(FR-018)

**Decision**:

- 目次の項目は、全章(`##`)と、人物・エンディング・その他報酬の `###` とする。場面内の
  調査対象は載せない。
- 幅の広い画面(Tailwind の `lg` 以上)では、本文の横に `sticky` で常に表示する。
- 幅の狭い画面では、画面右下に固定した「目次」ボタンから開くパネルとして出す。項目を選ぶと
  パネルを閉じて移動する。パネルには、ヘッダーのモバイルメニューで使っている
  `@headlessui/react` の `Dialog` を使う。
- 各見出しの id は見出し文字列から作る(空白を `-` に置換し、重複には `-2` などの連番を付ける)。
  固定ヘッダーに隠れないよう、見出しに `scroll-margin-top` を付ける。
- 開閉状態を持つのは目次だけなので、`"use client"` は目次コンポーネントだけに付ける。本文は
  サーバーコンポーネントのまま描画する。

**Rationale**: 2 操作以内での到達(SC-005)を満たす最小構成。狭い画面では「目次を開く→項目を
選ぶ」の 2 操作、広い画面では 1 操作になる。

**Alternatives considered**:

- 現在位置のハイライト(スクロールスパイ): spec の要件にない。`IntersectionObserver` の管理が
  増えるため見送る(原則1)。
- 場面内の調査対象まで目次に載せる: 長いシナリオでは項目が 100 を超え、目次自体が探しにくく
  なる。

## R7. 幅 375px での表示(FR-014)

**Decision**: 能力値は「項目名と値の組」をグリッドで並べ、狭い画面では 4 列、広い画面では
8 列にする。GFM の表は横スクロール可能な枠(`overflow-x-auto`)で包み、ページ全体には横
スクロールを発生させない。

**Rationale**: 表の列数は本文側で決まり、折り返しで崩すと読めなくなる。表単体のスクロールは
「ページの横スクロール」に当たらない、と解釈する。従来表示でも `prose` の中で同じ状況が
起きており、挙動を揃えられる。

## R8. 情報の欠落がないことの確認(FR-028 / SC-008)

**Decision**: 次の 2 段で確かめる。

1. **網羅性のユニットテスト**: 分割関数の出力(見出し + 各区画の本文)を元の順に連結すると、
   入力の Markdown と一致すること(サブタイトル・リードを含む)をテストする。どの行も構造の
   どこかに必ず属し、捨てられないことが保証される。
2. **データ適合テスト**: `structured: true` が付いた実シナリオすべてについて、次を確かめる。
   - 固定セクション名の章どうしが規約の順に並んでいる(FR-017)。場面の章の位置は問わない。
     parasite の `## 仕事終了後` のように、クライマックスの後に場面が続く構成もありうるため
   - 人物の `#### ステータス` から能力値を 1 つ以上読み取れる
   - 解釈できない能力値行が残っていない

   移行の完了条件は、このテストが通ることと、移行前後の目視での見比べとする。

**Rationale**: 本文そのものは書き換えないため、欠落が起きうるのは「解釈で行を捨てる」場合と
「移行時の手直しで消す」場合の 2 通りに限られる。前者はテスト 1 で、後者は git の差分
(移行コミットの diff)と目視確認で押さえられる。

## R10. 読み上げ文の記法(FR-023)

**Decision**: 1 行目が `[!読み上げ]` だけの引用を読み上げ文とする。

```markdown
> [!読み上げ]
> 扉を開けると、湿った土の匂いが鼻をつく。  
> 薄暗い部屋の奥で、何かが **〈聞き耳〉** に引っかかるような音を立てた。
```

構造化表示では、`ScenarioMarkdown` の引用(`blockquote`)の描画で 1 段落目の先頭を見る。
`[!読み上げ]` で始まっていれば目印を取り除き、読み上げ文の枠で囲む。それ以外の引用は従来
どおりセリフとして表示する。

**Rationale**:

- 引用の中は通常の Markdown なので、行末スペース 2 つの改行や判定の太字がそのまま使える。
  地の文と同じ書き方で描写を書ける(US6 受け入れ条件 4)。
- 生 HTML(`rehype-raw`)も新しい依存も要らない。`[!…]` は GitHub の Alert 記法と同じ形なので
  見慣れており、対応する定義のないリンク参照として文字列のまま残るので、Markdown として壊れない。
- 目印が無ければ、今までどおりのセリフ(引用)になる。既存の本文に影響しない。

**Alternatives considered**:

| 案 | 却下理由 |
| -- | -- |
| 言語指定付きのコードブロック(` ```読み上げ `) | コードブロックの中では太字や改行の記法が効かず、判定を含む描写が書けない。作中テキスト(言語指定なしのコードブロック)とも紛らわしい |
| 専用の見出し(`#### 読み上げ`) | 見出しは構造(区画)の区切りに使っているので、文章の装飾と混ざる。目次や網羅性の扱いも複雑になる |
| `remark-directive` の `:::read` 記法 | 依存が増える(原則1、ADR-0012) |

**従来表示での扱い**: 未移行のシナリオでは、目印の行が文字列として見える通常の引用になる。
読み上げ文は構造化表示のための指定として、移行済みのシナリオでだけ使う(spec Edge Cases)。
既存本文の移行で読み上げ文に書き換えることは必須としない(FR-023)。
