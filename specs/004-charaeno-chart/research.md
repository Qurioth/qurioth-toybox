# Phase 0 Research: 6版のキャラクターシート対応

**Feature**: [spec.md](./spec.md) / **Plan**: [plan.md](./plan.md)

**Date**: 2026-08-23

spec の Technical Context に残っていた不明点と、実装方針を決めるうえで先に確かめておく必要が
あった事項をまとめる。

---

## R1: レーダーチャートで能力値ごとに上限を変えられるか(FR-017)

**Decision**: 変えられない。代わりに**各能力値を「自分の上限に対する割合(0〜100)」へ正規化して
から渡す**。チャート側の目盛りは今の `[0, 100]` のまま変えない。これにより FR-017 の第一案
(6版は EDU が 21、それ以外が 18 を上限)をフォールバックなしで満たせる。

**Rationale**:

- 現在の [CharacteristicsRadarChart.tsx](../../src/components/recharts/CharacteristicsRadarChart.tsx)
  は `RadarChart` に `PolarRadiusAxis` を1つだけ置いている。recharts の RadarChart は半径軸を
  1本しか持たないため、軸(能力値)ごとに `domain` を変えることは構造上できない。
- 一方この画面は、チャートに **`Tooltip` も `Legend` も置いておらず、半径の目盛りも
  `tick={false}` で消している**。つまり利用者が能力値の生の数値をチャート上で読む経路が無い。
  したがって渡す値を正規化しても、利用者から見て嘘になる情報は出ない。生の値は表面の
  タイルと裏面の技能表にしか出ないが、そこは能力値ではない。
- 正規化は「STR 8 / 上限 18 → 44.4」のような単純な比の計算で、7版は上限が8つとも 100 なので
  `value / 100 * 100 = value` となり、**7版の見た目は一切変わらない**(SC-006)。

**Alternatives considered**:

| 案 | 却下理由 |
|---|---|
| 6版だけ `domain` を `[0, 21]` にする | FR-017 が「実現できない場合に限り」許した代替案。EDU 以外の7つが本来 18 上限なのに 21 で描かれ、能力値の高低がわずかに歪む。正規化で第一案が実現できる以上、選ぶ理由がない |
| RadarChart を能力値ごとに重ねる | recharts の想定外の使い方で、凡例・当たり判定・レスポンシブが破綻する。複雑さに見合わない(原則1) |
| `PolarRadiusAxis` を8本置く | 上と同じ。RadarChart は複数半径軸を想定していない |

**影響**: `CharacteristicsRadarChart` は変更不要。正規化はカード用データを組み立てる側で行う。
既存データに入っていて未使用の `fullMark` は、正規化後は意味を持たないため落とす。

## R2: 6版レスポンスの実データと型定義のずれ

**Decision**: [Charaeno6th.ts](../../src/types/Charaeno6th.ts) は**変更しない**。

**Rationale**:

- 6版の型定義は既にリポジトリにあるが未使用(`grep` で参照ゼロ)。
- 実データ(手元の3件)には `attribute.luck` / `attribute.idea` / `attribute.know` が入っているが、
  型定義には無い。FR-014 でこれらは表示しないと決めたため、型に足す必要がない(原則1)。
- 足すと「型にあるのに使わないフィールド」が増え、後から見た人が表示すべきか迷う。

**Alternatives considered**: 実データに合わせて `luck` / `idea` / `know` を型に追加する →
表示しないと決めたものを型に載せる意味がなく、YAGNI に反する。

## R3: 版の判定とサマリー取得先の組み立て(FR-012 / FR-013)

**Decision**: シートURLの正規表現を1本に統一し、そこから版とIDを同時に取り出す。
入力欄の検証(react-hook-form の `pattern`)とサマリーURLの組み立てで**同じ正規表現を共有**する。

```text
^https://charaeno\.com/(6th|7th)/<id>$
        └ 版 ┘        └ ID ┘
```

**Rationale**:

- 現状は [page.tsx](../../src/app/trpg/charaeno-chart/page.tsx) の `pattern` と
  [charaeno-utils.ts](../../src/utils/charaeno-utils.ts) の `SHEET_URL_PREFIX` に `7th` が
  二重に直書きされている。片方だけ 6th に対応させると、検証は通るのに取得先が 7th のまま、
  という壊れ方をする。定義を1箇所に寄せることでこの不整合を構造的に防ぐ。
- 「6版・7版以外の版を指すURLは形式が不正として扱う」(Edge Cases)は、この正規表現が
  `(6th|7th)` に限定されることで自動的に満たされる。`/8th/...` は検証で弾かれ、
  既存の「URLの形式が不正です。」が出る。

**Alternatives considered**: URL から `new URL()` でパス分解して判定する → ID に使える文字の
検証が別途必要になり、正規表現1本より複雑になる。現行の書き方(正規表現)から離れる利点もない。

## R4: 取得内容の検証を版ごとに分ける(FR-018)

**Decision**: `isInvestigator` を版ごとの型ガード2つに分け、両版で共通して必要な部分は
共有ヘルパにまとめる。呼び出し側は判定済みの版に対応するガードだけを通す。

両版で共通して必要: `name`(文字列) / `note`(文字列) / `skills`(配列) / `characteristics` の
8能力値(数値) / `attribute.hp`・`attribute.mp`(数値) / `attribute.san.value`(数値)

7版のみ必要: `backstory`(配列) / `attribute.luck`(数値)

6版のみ必要: `mentalDisorder` / `mythosTomes` / `artifactsAndSpells` / `attribute.db`
(いずれも文字列)

**Rationale**:

- 現在の `isInvestigator` は `backstory` と `attribute.luck` を必須にしている。6版の
  レスポンスにはどちらも無いので、そのまま通すと必ず「形式が想定と異なります」になる。
- 6版固有の項目を必須にしたのは、裏面の3項目は空文字判定を行うため、`attribute.db` は表面の
  タイルに出すため。省略された値が来ると判定側で扱いを増やすことになり、「必要な項目が
  揃っているかの最低限の確認」(FR-018)を素直に書けなくなる。実データ3件ではいずれも常に
  存在した(空文字であることはある)。
- `attribute.db` は7版のレスポンスにもあるが、7版のカードには出さないので7版側では必須に
  しない。「その版のカードを描くのに必要な項目だけを見る」という FR-018 の方針どおり。

**Alternatives considered**:

- 1つのガードで両版を受ける(どちらかの形を満たせば true) → 6版のURLに7版の形のJSONが
  返ってきても通ってしまい、FR-013 の「一方の版のURLにもう一方の版の内容」を検出できない。
- 6版固有の3項目を任意扱いにする → 描画側で毎回「文字列か」を見る必要が出る。検証を
  境界に寄せる今の設計と噛み合わない。

## R5: カードを版に依存しない形にする

**Decision**: 版ごとのレスポンス型を、**カードが描くために必要な情報だけを持つビューモデル**に
変換してから `CharacterCard` に渡す。`CharacterCard` は版を知らない。

**Rationale**:

- `CharacterCard` は現在、レスポンス型から表示物を導く処理(バックストーリーの見出し差し替え、
  技能の絞り込み、タイルの組み立て、チャート用データの整形)を内部に持っている。ここを版で
  分岐させると、レイアウト・反転アニメーション・チャートのマウント制御という既に複雑な
  コンポーネントに、さらに3箇所の分岐が入る。
- 変換を外に出せば、カードは「名前・立ち絵・チャート・タイル・技能・セクション」を受け取って
  並べるだけになり、テストも素朴な作りものデータで書ける。
- 将来の版を見越した抽象化ではない(原則1)。6版・7版という**今実在する2つ**を1つの表示形に
  合流させるだけで、版の登録機構やプラグインのような仕掛けは作らない。

**Alternatives considered**: `CharacterCard` に判別可能なユニオン(`{edition, data}`)を渡して
内部で分岐する → 変換処理そのものは消えず、複雑なコンポーネントの中に残る。カードの
テストが常に「版ごとの完全なレスポンス」を用意する形になり、書きにくさも変わらない。

---

## R6: 裏面のセクションの表し方(FR-015)

**Decision**: セクションを `{ heading, kind, blocks }` の一様な形で表す。`kind` は
`"list"`(箇条書き)と `"text"`(段落)の2つ。

- 7版のバックストーリー → `kind: "list"`。各 `block` が1つの項目で、改行で行に分けて表示する
  (現行の見た目のまま)。
- 7版のメモ / 6版の4項目 → `kind: "text"`。各 `block` が1段落で、空行で区切って表示する
  (現行のメモの見た目のまま)。

**Rationale**:

- 7版のバックストーリーは複数の記入欄が並ぶので箇条書きが合うが、6版の「読んだ魔導書」等は
  改行を含む自由記述の塊で、箇条書きにすると1項目に長文がぶら下がって読みにくい。既存の
  メモと同じ段落表示が素直。
- 見た目の種類は実際に2つあるので、フラグ1つで表す。これ以上の一般化はしない。

**Alternatives considered**: すべて段落表示に統一する → 7版の裏面の見た目が変わる。今回の
改修で7版に手を入れない方針(spec の Assumptions)から外れ、退行のリスクだけが増える。

---

## R7: 表面のタイルの4枠目(FR-014)

**Decision**: タイルの並びは `grid-cols-4` 固定のままにする。6版の4枠目には、幸運の代わりに
ダメージ・ボーナスを「DB」というラベルで出す。

**Rationale**:

- 当初は6版を HP・MP・SAN の3つにする想定で、タイル数に応じて `grid-cols-3` /
  `grid-cols-4` を出し分ける設計にしていた。6版の4枠目をダメージ・ボーナスで埋める決定に
  変わったため、どちらの版も4つになり、出し分けは到達しない分岐になった。使われない
  柔軟性は残さない(原則1)。
- ダメージ・ボーナスは「+0」「+1D4」のような文字列で、数値ではない。カード用ビューモデルの
  タイルの値を `number | string` に広げ、変換せずそのまま渡す。数値へ寄せようとすると
  「+1D4」を表現できない。
- 7版のレスポンスにも同じ `db` があるが、7版のカードには出さない。7版の表示は変えない方針
  (SC-006)のため。

**Alternatives considered**:

- タイル数の出し分けを残しておく → 今どちらの版も4つなので、`grid-cols-3` を選ぶ経路が無い。
  テストも実際には描かれない形を確かめることになる。
- ダメージ・ボーナスを数値に変換して持つ → 「+1D4」のようなダイス表記を落とすことになる。

**注意**: Tailwind は文字列連結で組み立てたクラス名を検出できないため、将来また出し分けが
必要になった場合も `grid-cols-${n}` とは書けない。完全なクラス名で分岐すること。

## R8: サンプルキャラクター一覧への波及

**Decision**: [sample-character/page.tsx](../../src/app/trpg/charaeno-chart/sample-character/page.tsx)
は、7版のJSONをビューモデルへ変換してから `CharacterCard` に渡す形に直す。**表示内容は変えない**。

**Rationale**: R5 でカードの受け取る形が変わるため、機械的な追従が必要。6版のサンプルは
追加しない(spec の Assumptions)。

## R9: テストの範囲

**Decision**: 既存のテスト3ファイルの延長で書く。新しいテスト基盤・フィクスチャの置き場は
作らない(原則6、ADR-0008)。

| ファイル | 追加する内容 |

| `src/utils/character-card-utils.test.ts`(新規) | 能力値の正規化(6版はEDUのみ21基準、7版は素通し)、タイルの内容、セクションの内容と順序、空項目の除外 |
| `src/components/CharacterCard.test.tsx` | ビューモデルを受ける形へ追従。数値でないタイルの値(DB)も描けること |
