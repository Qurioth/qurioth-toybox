# 0002. Spec-Driven Development (spec-kit) を導入する

## ステータス

Superseded by [ADR-0009](0009-adopt-official-spec-kit-cli.md)

## 日付

2026-07-30

## コンテキスト

これまで `qurioth-toybox` は仕様や設計をドキュメント化せず、思いついたまま実装するスタイルで
一人で開発してきた。今後もソロ開発を続ける方針だが、AIエージェント(Claude Code)を開発の主体的な
担い手として活用していきたい。AIにいきなり実装させると、要件の解釈違いや過剰実装、後から
「なぜこの仕様にしたか」が分からなくなる問題が起きやすい。

[GitHub spec-kit](https://github.com/github/spec-kit) が提唱する Spec-Driven Development (SDD) は、
実装前に「何を・なぜ作るか(spec)」→「どう作るか(plan)」→「具体的な作業(tasks)」の順で
ドキュメントを固めてから実装に入るワークフロー。AI駆動開発と相性が良く、一人開発でも仕様が資産として
残る。

なお、公式の `specify` CLI (spec-kit) は Python 3.11+ を要求するが、開発機には Python 3.10 しか
入っていないため、今回は CLI 導入は見送り、spec-kit と同等のディレクトリ構成・テンプレート・
Claude Code 用スラッシュコマンドを手動で再現した。Python 3.11+ が利用可能になった時点で、
`uvx --from git+https://github.com/github/spec-kit.git specify init --here` 等で公式CLI管理下に
移行できる。

## 決定

- ある程度まとまった機能追加・変更には SDD のフローを採用する。
  1. `/specify` で `specs/<番号>-<slug>/spec.md` に要件を記述(実装方法は書かない)
  2. `/plan` で技術方針を `plan.md` に落とす
  3. `/tasks` で実行可能な作業単位に分解する
  4. 実装し、必要なら ADR に大きな技術判断を記録する
- プロジェクト全体の開発原則を `.specify/memory/constitution.md` に定義する。
- typoや依存更新など影響の小さい変更にはこのフローを適用しない。
- spec-kit 公式CLIが使える環境になったら、手動再現した構成を公式CLI管理下に置き換えることを
  検討する。

## 影響・トレードオフ

- 良い点: 実装前に要件・設計をAIと人間の双方が確認できる。仕様がリポジトリに資産として残り、
  後から機能追加する際の文脈になる。AIへの丸投げによる過剰実装や要件の食い違いを減らせる。
- コスト: 小さな変更に対しても形式的なドキュメントを書きたくなる誘惑があるため、適用範囲を
  意識的に絞る必要がある。公式CLI不在のため、テンプレートの追従・更新は手動で行う必要がある。
