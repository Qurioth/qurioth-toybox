# 0001. Architecture Decision Record を記録する

## ステータス

Accepted

## 日付

2026-07-30

## コンテキスト

`qurioth-toybox` は個人開発のプロジェクトであり、これまで技術選定や設計判断の理由を明文化せずに
進めてきた。AIエージェント(Claude Code)を開発に本格的に取り入れるにあたり、「なぜその設計に
したか」という文脈が失われると、AIも人間(将来の自分)も過去の判断を再現・尊重できず、同じ議論を
繰り返したり、意図せず過去の決定を覆したりするリスクが高まる。

## 決定

Michael Nygard 形式に準拠した軽量な ADR (Architecture Decision Record) を `docs/adr/` 配下に
`NNNN-title.md` の形式で記録する。各 ADR には以下を含める。

- ステータス(Proposed / Accepted / Deprecated / Superseded by ADR-000X)
- 日付
- コンテキスト(なぜこの決定が必要になったか)
- 決定(何を決めたか)
- 影響・トレードオフ(この決定によって何が得られ、何を犠牲にするか)

対象は影響範囲の広い技術選定・アーキテクチャ変更のみとし、日々の実装の細部までは記録しない。

## 影響・トレードオフ

- 良い点: 技術判断の背景が残り、Claude Code を含む将来の作業者(自分自身)が文脈を踏まえた提案・
  実装ができる。
- コスト: 意思決定のたびにドキュメントを書く一手間が増える。ただし対象を「大きな判断」に絞ることで
  負担を最小限にする。
